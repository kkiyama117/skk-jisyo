# jisyo spec

## Purpose

`jisyo` is a Rust library and CLI for SKK dictionary data. It has two parts:

1. **Formats.** Read and write SKK-JISYO text in EUC-JP, EUC-JIS-2004, UTF-8 (with or without BOM), and UTF-16LE (with BOM), so that reading a file and writing it back gives the same bytes. Turn a file into its meaning (a `Dict`) and a `Dict` into the user-dictionary file of CorvusSKK, fcitx5-skk, or skkeleton.
2. **Store.** Keep an append-only local log of this machine's learning and a local cache of records fetched from a personal server. The own log also holds records waiting to be sent. Fetched records retain their original machine, sequence number, and time. Merging the records available locally gives the same `Dict` for the same record set in any arrival order. Offline input and learning use this local state without waiting for the server. The existing `sync` operation imports changes from a local IME file and exports a merged file; it is not network synchronization.

The decisions above this spec are ADRs by `skk-design` (`/data/softwares/skk/docs/adr/`). ADR-0006 proposes a personal server and a local record cache; its transport details remain Proposed, not an owner-approved wire protocol. This store revision follows that proposal and ADR-0009 section 4. `LearnEvent`, `LearnOp`, and `LogRecord` retain their existing shapes. The engine's `Output::Learn` carries a `jisyo::LearnEvent`. The server protocol, authentication, encryption, delivery acknowledgments, single-writer enforcement, and machine-ID recovery need separate specifications and review before transport cards run.

## Layers

The code is split only where there are really two or more implementations. A layer uses only the layers above it in this table.

| Layer | Modules | Rule |
|---|---|---|
| Core | `model`, `entry`, `dict`, `record`, `merge`, `diff` | Pure functions over the contract types, `&str`, and `&[u8]`. No files, no clock, no encoding tables, no knowledge of any IME. The engine will use this layer as it is: it emits `LearnEvent`s, and `merge` gives the user dictionary |
| Formats | `encoding`, `text`, `ime` | Pure functions between bytes and the core types: the four encodings, the lossless file model, and one `Profile` per IME. A new encoding or a new IME changes this layer only |
| Application | `sync` | The pure plan of one sync: given the bytes of every file and the time, return the bytes to write. All the guards live here |
| Outside | `store`, `main`, future server transport | File-system access, the real clock, and future network I/O stay here. Local IME sync reads cached records, calls `sync::plan`, and writes its results. Server exchange is separate and must not block key processing or local learning. Core, Formats, and Application contain no network I/O |

## Owns, reads, writes

| Owns | Reads | Writes | Must not |
|---|---|---|---|
| The log and snapshot files in a store directory the caller names | Dictionary files the caller names, the store directory | Only the paths the caller names: `--store`, `--file`, `--out` | Name any default path. Print, log, or put in an error a midashi, a candidate, an annotation, or a line of a dictionary: only counts, line numbers, byte offsets, and error codes. ## Contract

## Errors

Every fallible public function returns `Result<_, Error>`. An `Error` carries a code and, where this spec says so, a line, an offset, or a count. It never carries text from a dictionary or a log. `Display` gives `<code>` and then ` line <n>`, ` offset <n>`, ` count <n>`, ` io <kind>` for each field that is set, for example `decode offset 17`. `From<std::io::Error>` gives `io` with the error's kind.

| Code | When |
|---|---|
| `io` | A file operation failed |
| `decode` | Bytes are not valid in the encoding. `offset` is the byte offset in the file of the first byte of the bad sequence |
| `encode` | A character has no code in the encoding. `line` (when writing a `Jisyo`) and `offset` (byte offset of the character in the UTF-8 text of that line, or of the whole text for `Codec::encode`) |
| `unknown-coding` | The first line has a `coding:` cookie that names no encoding we know. `line` 1 |
| `not-round-trip` | A file decodes, but encoding the text again does not give the same bytes. `offset` is the first differing byte offset in the file |
| `bad-field` | A `LearnEvent` breaks a rule in "Field rules" |
| `bad-machine-id` | A machine ID breaks the rule in "Log" |
| `log-header` | A log's first line is not the header. `line` |
| `log-syntax` | A log line is malformed. `line` |
| `log-seq` | A log's sequence numbers do not go 1, 2, 3, ... `line` |
| `log-time` | A log's times do not strictly increase, or an append starts at or before the last time. `line` for a read |
| `log-conflict` | Two records have the same machine and sequence number but differ |
| `partial-tail` | The own log ends without a newline, so it cannot be appended to |
| `too-many-deletes` | An import would delete more candidates than allowed. `count` is the number |
| `target-missing` | A snapshot exists but the IME file does not |
| `unparsed` | The IME file has lines that are neither blank, comment, marker, nor entry. `line` is the first, `count` the number |
| `usage` | Bad CLI arguments |

## Encodings (`src/encoding.rs`, formats)

```rust
pub struct Codec { /* private */ }
impl Codec {
    pub fn new(encoding: Encoding) -> Codec;
    pub fn encoding(&self) -> Encoding;
    pub fn decode(&self, bytes: &[u8]) -> Result<String, Error>;
    pub fn encode(&self, text: &str) -> Result<Vec<u8>, Error>;
    pub fn can_encode(&self, text: &str) -> bool; // encode(text).is_ok()
}
```

`Codec` does not handle a BOM. `text.rs` strips and adds the BOM. `Codec::new` builds its maps from the embedded table each time it is called. There is no global state.

### Tables

`EucJis2004` uses `include_str!("../data/euc-jis-2004-std.txt")`. `EucJp` uses `include_str!("../data/euc-jp.txt")`. Both files have the same line format, and one parser reads both:

- A line that starts with `#` is a comment.
- Other lines are tab-separated. Field 1 is `0x` followed by 2, 4, or 6 uppercase hex digits: the code bytes, big-endian. Field 2 is `U+` followed by 4 to 6 hex digits, optionally followed by `+` and 4 to 6 more hex digits for a pair of code points. The parser ignores the rest of the line.
- The parser skips a line whose field 2 is empty, a single-byte code of `0x80` or more, and a line that does not match. A test checks the counts below, so a skipped line that should not be skipped shows up there.

| Encoding | Single bytes (0x00–0x7F) | 0x8E kana | Two bytes 0xA1A1–0xFEFE | 0x8F three bytes | Total | Of which pairs |
|---|---|---|---|---|---|---|
| `EucJis2004` | 128 | 63 | 8,797 | 2,436 | 11,424 | 25 |
| `EucJp` | 128 | 63 | 6,879 | 6,067 | 13,137 | 0 |

No two codes in one table decode to the same string (a test checks this).

### EUC decode

At byte `b` at offset `i`:

- `b < 0x80`: one byte.
- `b == 0x8E`: two bytes `[0x8E, x]`.
- `b == 0x8F`: three bytes `[0x8F, x, y]`.
- `0xA1 <= b <= 0xFE`: two bytes `[b, x]`.
- Any other `b`, a sequence cut off by the end of the input, or a sequence that is not in the table: `decode` with offset `i`.

A code that maps to a pair gives both code points.

### EUC encode

Walk the characters of the text. At each character, first try it together with the next character as a pair. If the table has the pair, emit its code and move past both. Otherwise look up the single character, first in the table and then in the aliases below. If neither has it, return `encode` with the byte offset of the character in the text.

Aliases are used only for encoding, and only for characters that are not in that table. They let words typed on Windows (CP932 forms) and words from the other EUC table be written:

| Encoding | Character → code |
|---|---|
| `EucJis2004` | U+FFE3→A1B1, U+2015→A1BD, U+FFE5→A1EF, U+FFE0→A1F1, U+FFE1→A1F2, U+FFE2→A2CC |
| `EucJp` | U+203E→A1B1, U+2014→A1BD, U+00A5→A1EF, U+2225→A1C2, U+FF0D→A1DD, U+FFE0→A1F1, U+FFE1→A1F2, U+FFE2→A2CC |

Eleven of the 25 EUC-JIS-2004 pairs (0xABC4, 0xABC8, 0xABC9, 0xABCA, 0xABCB, 0xABCC, 0xABCD, 0xABCE, 0xABCF, 0xABE5, 0xABE6: IPA letters with a combining accent or a tone letter) can also be written as two single codes. The other 14 (kana with U+309A) cannot, because U+309A has no single code. A file that uses the two single codes decodes to the same text, and encoding gives the pair code. `text::read` refuses such a file with `not-round-trip`. That is the intended behavior.

### UTF-8 and UTF-16LE

- `Utf8` decode is `std::str::from_utf8`. On error, `decode` with offset `valid_up_to()`. Encode is the bytes of the text and never fails.
- `Utf16Le` decode reads little-endian 16-bit units. An odd length gives `decode` with offset `len - 1`. An unpaired surrogate gives `decode` with offset `2 * <index of the unit>`. Encode is `encode_utf16` as little-endian bytes and never fails.

### `data/euc-jp.txt`

`tools/gen-euc-jp.py` (Python standard library, plus the `iconv` program through `subprocess`) writes it:

- Header, exactly two lines: `# EUC-JP vs Unicode mapping table, generated by tools/gen-euc-jp.py from glibc iconv EUC-JP.` and `# Do not edit. Regenerate with: python3 tools/gen-euc-jp.py`.
- Then one line `0x%02X\tU+%04X` for each byte 0x00–0x7F, mapped to the same code point.
- Then one line `0x%0NX\tU+%04X` (`N` is 4 or 6, uppercase hex, at least 4 hex digits of code point) for each candidate code that is kept. The candidates are `0x8E` + 0xA1..=0xFE, 0xA1..=0xFE × 0xA1..=0xFE, and `0x8F` + 0xA1..=0xFE × 0xA1..=0xFE. A code is kept when `iconv -f EUC-JP -t UTF-8` decodes it to exactly one character and `iconv -f UTF-8 -t EUC-JP` encodes that character back to the same bytes. Both checks are needed: with `-c`, iconv can skip a bad lead byte and decode the rest as another character.
- Lines are in ascending order of the code as an unsigned integer. The file ends with a newline.
- `python3 tools/gen-euc-jp.py` writes the file. `python3 tools/gen-euc-jp.py --check` builds the same text in memory and exits 1 if the file differs, else 0. The gate does not run the script, because the result depends on the glibc version.

## One entry line (`src/entry.rs`, core)

```rust
pub fn parse_candidate(token: &str) -> Candidate;
pub fn format_candidate(c: &Candidate) -> String;
pub fn parse_entry(content: &str, section: Section) -> Option<Entry>;
pub fn format_entry(entry: &Entry) -> String;
```

- `parse_candidate`: `word` is the text before the first `;`. `annotation` is `Some(text after it)` when there is a `;` (possibly `Some("")`), else `None`.
- `format_candidate`: `word`, then `;` and the annotation when it is `Some`.
- `format_entry`: `midashi`, then ` /`, then `<candidate>/` for each candidate, then for each block `[<okuri>/`, then `<candidate>/` for each of its candidates, then `]/`. Examples: `かんじ /漢字/感じ/`, `おおk /大/多/[く/多/]/[き/大/]/`, `おおk /[く/]/` (an empty block), `かんじ /` (no candidates).

`parse_entry(content, section)`:

1. `midashi` is the text before the first space (U+0020). There must be a space, `midashi` must not be empty, and it must not start with `;`.
2. The rest after that space, `R`, must start with `/`. Split `R` without its first character on `/`. The last piece must be empty (that is, `R` ends with `/`). Drop it. The other pieces are the tokens, in order.
3. An empty token makes the line not an entry.
4. In `OkuriNasi`, every token is a candidate.
5. In `OkuriAri`, a token that starts with `[` opens a block. Its `okuri` is the token without the `[`. The `okuri` must not be empty and must not contain `[` or `]`. The tokens after it, up to a token that is exactly `]`, are the block's candidates. Such a token must not start with `[`. A missing `]` makes the line not an entry. Once the first block opens, every later token must open a block. A token `]` outside a block makes the line not an entry.
6. A candidate token goes through `parse_candidate`. An empty `word` makes the line not an entry.
7. Finally, `parse_entry` returns `Some` only when `format_entry` of the result equals `content`. Otherwise it returns `None`. This rule keeps entries lossless. A line with two spaces after the midashi, or with text after the last `/`, is `None`.

## One file (`src/text.rs`, formats)

```rust
pub fn detect(bytes: &[u8]) -> Result<(Encoding, bool), Error>; // (encoding, has BOM)
pub fn read(bytes: &[u8], forced: Option<Encoding>) -> Result<Jisyo, Error>;
pub fn write(jisyo: &Jisyo) -> Result<Vec<u8>, Error>;
pub fn line_content(kind: &LineKind) -> String;
```

Constants: the markers are exactly `;; okuri-ari entries.` and `;; okuri-nasi entries.`.

`detect`, first rule that applies:

1. Starts with `EF BB BF`: `(Utf8, true)`.
2. Starts with `FF FE`: `(Utf16Le, true)`.
3. **Cookie.** The first line is the bytes before the first `0x0A`, or all bytes when there is none. If it starts with `;` and contains the ASCII bytes `coding:`, the name is what follows the first `coding:`, after skipping spaces and tabs: the longest run of ASCII letters, digits, `.`, `_`, `-`. Lowercase it and strip one suffix `-unix`, `-dos`, or `-mac`. Then `euc-jp`, `euc-japan`, `eucjp`, `japanese-iso-8bit` → `(EucJp, false)`; `euc-jis-2004`, `euc-jisx0213` → `(EucJis2004, false)`; `utf-8`, `utf8` → `(Utf8, false)`. Any other name, including an empty one, is `unknown-coding` line 1.
4. Valid UTF-8 (including pure ASCII and empty input): `(Utf8, false)`.
5. Decodes as `EucJis2004`: `(EucJis2004, false)`. ddskk writes EUC-JIS-2004 by default and without a cookie. libskk always writes a cookie.
6. Decodes as `EucJp`: `(EucJp, false)`.
7. Else the `decode` error of step 5.

`read(bytes, forced)`:

1. With `forced = Some(e)`, the encoding is `e`, and the BOM counts only when it matches `e` (`EF BB BF` for `Utf8`, `FF FE` for `Utf16Le`). With `None`, use `detect`.
2. Strip the BOM. Decode the rest with `Codec`. A `decode` offset is reported from the start of the file, BOM included.
3. **Round-trip guard.** Encode the decoded text again. If the bytes differ from the input after the BOM, return `not-round-trip` with the offset (from the start of the file) of the first byte that differs, or of the end of the shorter one.
4. Split the text on `\n`. Every piece except the last is a line. Its `eol` is `CrLf` when the piece ends with `\r` (which is removed from the content), else `Lf`. The last piece is a line with `eol` `None` when it is not empty, and no line when it is empty. An empty file has no lines.
5. Classify each line's content in order, with a current section that starts as none:
   - `""` → `Blank`.
   - exactly a marker → `Marker(section)`, and the current section becomes it.
   - starts with `;` → `Comment(content)`.
   - in a section, and `parse_entry(content, section)` is `Some(e)` → `Entry(e)`.
   - anything else, including every non-comment line before the first marker → `Other(content)`.

`line_content` gives the text of a line: `""`, the comment, the marker text, `format_entry`, or the other text.

`write`: for each line, its content and then `\n`, `\r\n`, or nothing for `Lf`, `CrLf`, or `None`. Encode line by line with `Codec`. An `encode` error gets `line` = 1-based index of the line and keeps the offset within that line's text. With `bom` true, prefix `EF BB BF` for `Utf8` or `FF FE` for `Utf16Le`. `bom` is ignored for the EUC encodings. `write` does not check that only the last line has `Eol::None`.

**Lossless rule.** For any bytes that `read` accepts, `write(&read(bytes, f)?)` equals `bytes`.

## Meaning of a file (`src/dict.rs`, core) and IME files (`src/ime.rs`, formats)

```rust
pub struct DictReport {
    pub dict: Dict,
    pub other_lines: Vec<u64>,      // 1-based line numbers of Other lines
    pub duplicate_lines: u64,       // entry lines whose midashi was already seen in the section
    pub duplicate_candidates: u64,  // candidates dropped because their word was already in the list
}
pub fn from_jisyo(jisyo: &Jisyo) -> DictReport;
pub fn without_blocks(dict: &Dict) -> Dict;
```

`src/ime.rs` (formats):

```rust
pub fn profile(target: Target) -> Profile;
pub fn target_name(target: Target) -> &'static str;   // "corvus", "fcitx5", "skkeleton"
pub fn parse_target(name: &str) -> Option<Target>;    // the inverse of target_name
pub struct Rendered { pub jisyo: Jisyo, pub skipped: u64 }
pub fn render(dict: &Dict, profile: &Profile) -> Rendered;
```

A **list** is the main candidates of an entry, or the candidates of one block. Its identity is `(section, midashi, okuri)`, with `okuri = None` for the main list. A candidate's identity within a list is its `word`. The annotation does not count.

`from_jisyo`: walk the lines and keep the current section from the markers. Each `Entry` line goes into that section's vector in file order. When the section already has an entry with the same midashi, merge into the first one and add 1 to `duplicate_lines`. Append the later line's candidates whose word is not yet in the main list. For each later block, append its new candidates to the block with the same okuri, or append the whole block when there is none. Inside any list, a candidate whose word is already in that list is dropped and adds 1 to `duplicate_candidates`. This includes repeats within one line. Blocks of one line with the same okuri merge the same way. `Other` lines go to `other_lines`. `without_blocks` returns a copy with every `blocks` vector empty.

`profile`:

| Target | encoding | bom | eol | cookie | blocks | Why |
|---|---|---|---|---|---|---|
| `Corvus` | `Utf16Le` | true | `CrLf` | none | true | CorvusSKK writes `userdict.txt` with `_wfopen` mode `wt,ccs=UTF-16LE` (text mode, CRLF) and writes okuri blocks |
| `Fcitx5` | `EucJp` | false | `Lf` | `;;; -*- coding: euc-jp -*-` | false | libskk writes this cookie, and it splits a line only on `/`, so a block would show up as candidates `[く` and `]` |
| `Skkeleton` | `Utf8` | false | `Lf` | none | true | skkeleton writes no cookie, keeps a `[...]` block as one opaque item, and filters it from the candidates |

`render(dict, profile)`: the lines are the cookie as a `Comment` line (when there is one), `Marker(OkuriAri)`, the `okuri_ari` entries in order, `Marker(OkuriNasi)`, and the `okuri_nasi` entries in order. Every line, the last included, has `eol = profile.eol`. The `Jisyo` has `profile.encoding` and `profile.bom`. Without `profile.blocks`, blocks are dropped and are not counted as skipped. Then, using `Codec::can_encode` for `profile.encoding`:

- an entry whose midashi cannot be encoded is dropped, and each of its candidates (main and blocks) adds 1 to `skipped`;
- a block whose okuri cannot be encoded is dropped, and each of its candidates adds 1;
- a candidate whose `format_candidate` text cannot be encoded is dropped and adds 1;
- a block left with no candidates is dropped, and an entry left with no candidates and no blocks is dropped. These add nothing more.

## Store

### Learning events

A `LearnEvent` is one thing the owner taught the dictionary, addressed to one candidate of one list. The engine will emit them as the owner types. `diff` produces the same events from what an IME changed in its file. A `LogRecord` is a `LearnEvent` plus who wrote it (`machine`), its place in that machine's log (`seq`), and when (`time`). The core never reads a clock: the outside layer gives the time.

| `LearnOp` | Engine moment | Effect after `merge` |
|---|---|---|
| `Add` | a word is registered | present, at the front of its list |
| `Promote` | a candidate is chosen and confirmed | present, at the front of its list |
| `Delete` | a candidate is purged (`X`) | absent |
| `Annotate` | an annotation is edited | the annotation changes, the position does not |

One keystroke can teach several lists. Confirming 動く for `うごk` is a `Promote` of 動 in the main list and a `Promote` of 動 in block `く`. The engine emits both, in that order.

**Promote producer contract.** For each target list `(section, midashi, okuri)`, the engine identifies the candidate by `word`. If that list in the user dictionary passed to the current `step` already contains the word, the event carries that candidate's complete current `word` and `annotation`. Otherwise it carries the selected lookup candidate, including its annotation. Displaying a candidate without annotations does not authorize dropping the annotation from the event. Preserve `None`, `Some("")`, and nonempty annotations as distinct values. Unknown or unrequested metadata must not be represented by `None`. An intentional annotation change or removal is an `Annotate`, not a side effect of selecting a candidate.

Resolve the main-list and block-list payloads independently. If they hold different annotations for the same word, keep each value in its own `Promote`; do not copy one list's annotation over the other. Use the selected lookup candidate only for a target list that does not yet contain the word. This does not guarantee preservation of another machine's annotation that the producer has not fetched.

`merge` and `apply` still apply the payload as written. They do not repair an incomplete producer payload by preserving an older annotation when the event says `None`. The engine's tests must check these production rules through public `step`; this crate's tests check the payload semantics through public `apply` and `merge`. No new engine lookup API is specified here.

### Record (`src/record.rs`, core)

```rust
pub const HEADER: &str = "jisyo-log 1";
pub fn validate_machine_id(id: &str) -> Result<(), Error>;
pub fn validate_event(event: &LearnEvent) -> Result<(), Error>;
pub fn format_record(record: &LogRecord) -> String;            // one line, without "\n"
pub struct LogRead { pub records: Vec<LogRecord>, pub partial_tail: bool, pub complete_len: usize }
pub fn parse_log(machine: &str, bytes: &[u8]) -> Result<LogRead, Error>;
pub struct Appended { pub bytes: Vec<u8>, pub records: Vec<LogRecord> }
pub fn append_bytes(machine: &str, existing: Option<&[u8]>, events: &[LearnEvent], first_time: u64) -> Result<Appended, Error>;
```

A machine ID matches `^[a-z0-9][a-z0-9-]{0,31}$`. Otherwise the error is `bad-machine-id`.

**Field rules** (`validate_event`, else `bad-field`). These are exactly what an SKK line can hold:

- `midashi` is not empty, has no space and no `\n`, and does not start with `;`.
- `okuri` is `None` in `OkuriNasi`. When it is `Some(k)`, `k` is not empty and has no `/`, `[`, `]`, or `\n`.
- `candidate.word` is not empty and has no `/`, `;`, or `\n`. In `OkuriAri` it does not start with `[` and is not `]`.
- `candidate.annotation`, when it is `Some`, has no `/` and no `\n`. A `Delete` has `annotation = None`.

**File.** UTF-8. The first line is exactly `jisyo-log 1`. Every later line is one record, and every line ends with `\n`. A record line has 8 tab-separated fields:

```
<machine>\t<seq>\t<time>\t<op>\t<section>\t<midashi>\t<okuri>\t<candidate>
```

- `seq` and `time` are decimal, with no sign and no leading zero (except `0` itself), and fit in `u64`. `seq` is 1 for the first record and goes up by 1. `time` strictly increases within a file.
- `op` is `add`, `promote`, `delete`, or `annotate`. `section` is `ari` or `nasi`.
- `okuri` is empty for the main list. `candidate` is `format_candidate`.
- The text fields (midashi, okuri, candidate) escape `\` as `\\`, tab as `\t`, LF as `\n`, and CR as `\r`. Any other `\x` is `log-syntax`. A raw CR anywhere in a line is `log-syntax`.

`parse_log(machine, bytes)`:

- The complete part is the bytes up to and including the last `\n`, and `complete_len` is its length. The rest is a **partial tail**, which can result from an interrupted write. It is ignored for reading, and `partial_tail` is set. This is not permission to publish a partially received server response as a completed cache update. Receive validation and atomic cache publication belong to the future transport contract. Appending to an own log with a partial tail remains forbidden.
- An empty complete part gives no records.
- Otherwise the first line must be the header (else `log-header` line 1).
- Each record line: invalid UTF-8, a field count other than 8, a machine field that is not `machine`, a bad number, op, section, or escape, or a field that breaks the field rules gives `log-syntax` with the line. A seq that is not the previous plus 1 gives `log-seq`. A time that is not greater than the previous gives `log-time`.

`append_bytes(machine, existing, events, first_time)` returns the bytes to append to the own log and the records they hold. The caller writes them.

1. Validate the machine and every event first.
2. Empty `events`: return no bytes and no records.
3. With `existing = Some(bytes)`, `parse_log` them. A partial tail is `partial-tail`. Take the last seq and time, or 0 and 0 when there are no records.
4. `first_time` must be greater than the last time (else `log-time`). Event `i` (0-based) gets `seq = last_seq + 1 + i` and `time = first_time + i`.
5. The bytes are the header line, when `existing` is `None` or empty, then one line per record.

### Merge (`src/merge.rs`, core)

```rust
pub fn merge(records: &[LogRecord]) -> Result<Dict, Error>;
pub fn apply(dict: &mut Dict, event: &LearnEvent);
pub fn next_time(now_ms: u64, records: &[LogRecord]) -> u64;
```

The result depends only on the set of records, never on their order. This is the property that lets any machine merge the logs in any order.

1. Records with the same `(machine, seq)` must be equal. A duplicate is used once. A pair that differs gives `log-conflict`.
2. Records are ordered by `(time, machine, seq)`, with `machine` compared as bytes. "Latest" means greatest in this order.
3. A candidate key is `(section, midashi, okuri, word)`. For each key:
   - **presence** is the latest record among `Add`, `Promote`, and `Delete`. The candidate is present when there is one and it is not `Delete`. Its **rank** is that record's order key.
   - **text** is the latest record among `Add`, `Promote`, and `Annotate`. The candidate's annotation is that record's annotation.
   - An `Annotate` alone does not make a candidate present.
4. **touch.** An entry's touch is the latest record of any op with its `(section, midashi)`. A block's touch is the latest record of any op with its `(section, midashi, Some(okuri))`. Deletes and annotates count, so purging a word also brings its entry to the front, as using one does. Entry and block order never changes what a lookup returns. It only changes the order of lines in an export and the order of completions, so an entry that comes to the front after a delete does no harm.
5. Build the `Dict` from the present candidates. A list holds its candidates by rank, highest first. An entry's blocks are ordered by touch, latest first. Each section's entries are ordered by touch, latest first. A block exists exactly when its own list has a present candidate. An entry exists exactly when its main list has a present candidate or at least one of its blocks exists. Candidates inside blocks therefore count for entry existence. An entry with an empty main list and a nonempty block is retained. An entry with neither main candidates nor nonempty blocks is omitted.

`apply(dict, event)` changes a `Dict` as one record later than every record behind it would. The engine's shell uses it to keep its in-memory dictionary current between merges (ADR-0009). In the event's section:

- `Add` or `Promote`: create the entry if missing (at the end of the section; it moves next), and the block if the event has an `okuri` and the block is missing. Remove the candidate's word from its list if present, then insert the event's candidate at the front.
- `Delete`: remove the word from its list if present. Remove a block left empty, then an entry left with no candidates and no blocks.
- `Annotate`: if the word is in its list, set its annotation to the event's. Otherwise do nothing to the candidates.
- Then, for every op, if the entry still exists, move it to the front of its section, and if the event has an `okuri` and that block still exists, move the block to the front of the entry's blocks.

**apply rule.** For any records `R` and a record `r` later than all of them, `apply(&mut merge(R), &r.event)` gives `merge(R ∪ {r})`.

`Add` and `Promote` have the same effect. Both say "this candidate is in the list, at the front, as of this time". The log keeps them apart for people reading it. A promote after a delete brings the candidate back, because the owner used it after deleting it.

`next_time(now_ms, records)` is `max(now_ms, 1 + the greatest time in records)`, or `now_ms` when there are no records. A record that a machine writes after it has read another machine's record is therefore later than that record, even when the clocks disagree.

### Diff (`src/diff.rs`, core)

```rust
pub fn diff(old: &Dict, new: &Dict) -> Vec<LearnEvent>;
```

`old` is the last export (the snapshot). `new` is what the IME wrote since. The result, applied in order with increasing times, turns each list of `old` into the same list in `new`.

**Per list.** Let `O` be the old list and `N` the new list (either may be empty):

1. `Delete` for each candidate of `O`, in `O` order, whose word is not in `N`.
2. Let `S` be the longest suffix of `N` whose words are all in `O` and whose positions in `O` strictly increase from left to right. Let `P` be the rest of `N`, before `S`. For `j` from the last index of `P` down to 0, emit `Add` of `P[j]` when its word is not in `O`, else `Promote` of `P[j]`. The candidate, with its annotation, is the one from `N`.
3. `Annotate` for each candidate of `S`, in `S` order, whose annotation differs from that word's annotation in `O`.

Move-to-front (ddskk, CorvusSKK, skkeleton) gives one `Promote` per use. libskk swaps the chosen candidate with the first one. `[a,b,c,d]` becomes `[c,b,a,d]`, which gives `Promote b`, then `Promote c`. This reproduces the new order exactly. An IME that appends new words at the end gives a `Promote` for every older candidate. That is noisy but still correct.

**Order of lists.** The times decide the order of entries after a merge, so the lists are processed in this order:

1. Lists of entries that are only in `old` (no entry with that midashi in that section of `new`): by section (`OkuriAri` first), then midashi as bytes, then okuri (`None` first, then bytes).
2. Then the entries of `new` in reverse file order: `okuri_nasi` from last to first, then `okuri_ari` from last to first. Within one entry: first the blocks that are only in `old`, by okuri as bytes, then the blocks of `new` from last to first, then the main list.

The first entry of the file then gets the latest times, which keeps the most-recent-first entry order of CorvusSKK and ddskk. Within an entry, the main list is last, so it gets the entry's latest time.

With `old` empty (the first import from an existing IME file), every event is `Add`, and `merge` of those events gives back `new` exactly, including entry and block order.

### Sync plan (`src/sync.rs`, application)

```rust
pub struct SyncInput<'a> {
    pub machine: &'a str,
    pub target: Target,
    pub logs: &'a [LogRecord],          // records available locally, own log included
    pub own_log: Option<&'a [u8]>,      // the own log's bytes, None when the file is missing
    pub snapshot: Option<&'a [u8]>,
    pub seen: Option<&'a [u8]>,         // the IME file as the previous sync read it
    pub ime_file: Option<&'a [u8]>,
    pub max_deletes: u64,
    pub skip_unparsed: bool,
    pub confirm_delivered_deletes: bool,
    pub now_ms: u64,
}
pub struct SyncReport { pub added: u64, pub promoted: u64, pub deleted: u64, pub annotated: u64, pub restored: u64, pub skipped: u64, pub bootstrap: bool }
pub struct SyncPlan { pub log_append: Vec<u8>, pub output: Vec<u8>, pub seen: Option<Vec<u8>>, pub report: SyncReport }
pub fn plan(input: &SyncInput) -> Result<SyncPlan, Error>;
pub fn export_bytes(target: Target, logs: &[LogRecord]) -> Result<(Vec<u8>, u64), Error>; // bytes, skipped
```

`plan`, in this order. It is pure: any error means nothing is to be written.

1. `p = profile(target)`.
2. If there is a snapshot: `old = from_jisyo(&read(snapshot, None)?).dict`.
3. If there is an IME file: `report = from_jisyo(&read(ime_file, None)?)`, `new = report.dict`. A snapshot without an IME file is `target-missing`. With neither, `old` and `new` are empty. An IME file without a snapshot sets `bootstrap`, and `old` is empty.
4. **Unparsed guard.** If `report.other_lines` is not empty and `skip_unparsed` is false, return `unparsed` with the first line and the count. An entry that we cannot parse would otherwise look deleted.
5. Without `p.blocks`, apply `without_blocks` to `old`, `new`, and the seen Dict below. `events = diff(&old, &new)`.
6. **Restore guard and explicit deletion confirmation.** The **delivered** keys are the `(section, midashi, okuri, word)` keys of `old` that are not in `seen` (`from_jisyo(&read(seen, None)?).dict`). With a snapshot but no `seen`, every key of `old` counts as delivered. By default `confirm_delivered_deletes` is false. Drop each diff-produced `Delete` whose key is delivered, and count it in `restored`. The absence creates no new Delete; the output follows the retained records and restores the candidate if it is still present in their merged state. When `confirm_delivered_deletes` is true, keep those actual diff-produced deletes and do not count them in `restored`. This confirmation creates no delete for a key that is not missing from `new`; step 7 still checks all retained deletes.

   `confirm_delivered_deletes` is an explicit user assertion that the currently missing delivered candidates were intentionally purged. The CLI sets it only for the current invocation's `--confirm-delivered-deletes`; it is false without that flag and is never persisted as a default. Automated watchers, repeated missing observations, file timestamps, retry counts, and server arrivals must not set it. The library caller has the same obligation to obtain explicit user intent for the current diff.

   A stale IME can repeatedly save the same missing-word file that an intentional repeated purge produces. With the same logs, snapshot, seen, and IME bytes, a file-only importer cannot distinguish those histories. Therefore an unconfirmed absence stays protected even on the second or later sync. Seeing the word absent twice is not confirmation. Do not claim that the word returns only once or that the second legacy-IME `X` alone is observable as intent. To complete a repeated purge before any sync has read the word in the IME file, the owner confirms that purge with the flag while the IME file still lacks the word. The resulting `Delete` is appended even though `seen` never contained it. A later purge after a sync has actually read the word in `seen` needs no special confirmation. An engine event with `op = LearnOp::Delete` is direct learning, not an absence inferred from an IME file, and is not filtered by this import guard.
7. **Delete guard.** If the number of `Delete` events left is greater than `max_deletes`, return `too-many-deletes` with the number. The CLI default is 10. This is the last net behind the restore guard.
8. `appended = append_bytes(machine, own_log, &events, next_time(now_ms, logs))`.
9. `merge` of `logs` plus `appended.records`, then `render` with `p`, then `write`. That is `output`. `skipped` is the render's count.
10. `seen` in the plan is a copy of `ime_file` (`None` when there is no IME file).

`export_bytes(target, logs)`: `merge`, `render` with the profile, `write`.

### Store (`src/store.rs`, outside)

```
<store>/logs/<machine>.log                 own append-only log or cached records of another machine
<store>/state/<machine>/<target>.jisyo       local last export for one target (the snapshot)
<store>/state/<machine>/<target>.seen.jisyo  local IME file as the last sync read it
```

`<target>` is `target_name(target)`. The Store's configured machine is the only producer of new records in its own log. That log is both local learning history and the outbox for future server delivery. Sending or acknowledging records does not delete or rewrite them. Each other `<id>.log` contains records fetched for that original machine, preserving every `machine`, `seq`, `time`, and event field. Storing such a replica does not authorize generating new learning under that machine's ID or restamping records on arrival. The local union of own and fetched records is the cache used for offline lookup, export, and IME sync. Records that have never been fetched are unavailable offline.

Snapshots and seen files are local bridge state for the configured machine and target. They are not learning records, are not uploaded to the server, and are not treated as another machine's learning. No shared folder or external folder-copy tool is required. Cache downloads and local IME `sync` are distinct operations. The initial policy keeps all complete records, including deletes and records already acknowledged by the server; compaction and ID recovery need separate contracts.

```rust
pub struct Store { /* dir, machine */ }
pub struct Logs { pub records: Vec<LogRecord>, pub ignored_files: u64, pub partial_tails: u64 }
pub struct SyncOptions { pub target: Target, pub file: PathBuf, pub max_deletes: u64, pub skip_unparsed: bool, pub confirm_delivered_deletes: bool, pub dry_run: bool }
pub struct SyncDone { pub report: SyncReport, pub written: bool }
impl Store {
    pub fn open(dir: &Path, machine: &str) -> Result<Store, Error>; // validates the ID, creates logs/ and state/<machine>/
    pub fn log_path(&self) -> PathBuf;
    pub fn snapshot_path(&self, target: Target) -> PathBuf;
    pub fn read_logs(&self) -> Result<Logs, Error>;
    pub fn sync(&self, options: &SyncOptions, clock: &dyn Clock) -> Result<SyncDone, Error>;
    pub fn export(&self, target: Target, out: &Path) -> Result<u64, Error>; // returns skipped
    pub fn repair_log(&self) -> Result<u64, Error>;                         // bytes removed
}
pub fn write_atomic(path: &Path, bytes: &[u8]) -> Result<(), Error>;
```

`read_logs` reads every regular file in `logs/` whose name is `<id>.log` with a valid ID, through `parse_log(id, ...)`. This includes the own log and cached other-machine logs. It performs no server request and never changes record identity, payload, or time. Any other file adds 1 to `ignored_files`, covering temporary or unrelated files without assuming an external synchronization tool. Each partial tail adds 1 to `partial_tails`. Reading a partial own log does not authorize a later append to it; `append_bytes` still returns `partial-tail`.

`sync`:

1. Read the locally cached logs, the own log's bytes, the snapshot, the seen file, and the IME file (a missing file is `None`). Build `SyncInput` with `clock.now_ms()` and this invocation's options, including `confirm_delivered_deletes`, and call `plan`. On error, write nothing. Do not contact the server or wait for an acknowledgment.
2. With `dry_run`, return the report with `written` false. Write nothing.
3. Append `log_append` to the own log: open for append (create if missing), one `write_all`, `sync_all`.
4. Write the IME file with `write_atomic` unless its bytes already equal `output`. Set `written`.
5. Then write the snapshot with `write_atomic`, with `output`.
6. Then, when the plan's `seen` is `Some`, write it to the seen file with `write_atomic`.

The order matters. If the process stops between steps 4 and 5, the next sync sees our own export as IME changes. Those events repeat merged records and lose nothing. If it stops between 5 and 6, the older seen file makes more keys count as delivered, which can only drop deletes, never add them. Any other order could make the merged words look deleted.

`write_atomic(path, bytes)`: write `<path>.jisyo-tmp` (create or truncate) in the same directory, `sync_all`, then rename it over `path`.

`export(target, out)`: `export_bytes` of all logs, then `write_atomic` to `out`. It does not touch the log or a snapshot.

`repair_log`: if the own log is missing, empty, or ends with `\n`, return 0. Otherwise truncate it after its last `\n` (or to 0 bytes when it has none), `sync_all`, and return the number of bytes removed.

### Server-exchange boundary

Network exchange is not part of `Store::sync`, `sync::plan`, or the current CLI commands. A future outside adapter sends the own records and fetches other machines' records. The server retains their union by `(machine, seq)`, accepts an identical retransmission once, and rejects different contents under the same ID with `log-conflict`. Neither download time nor server arrival order replaces a record's original time. The existing `(time, machine, seq)` order decides presence, annotation, rank, and touch everywhere.

The own log remains durable local history and outbox during disconnection and after acknowledgment. Do not claim a record is sent before the receiver has durably stored it. Delivery positions may reduce retransmission but do not change record identity. Do not delete records after sending. A cache update preserves previously accepted records and rejects conflicting replacements instead of overwriting them. The future receive contract must specify assembling and validating complete per-machine prefixes and atomic publication; a cut response is not a completed cached log. The own log's producer remains the local machine, not the download adapter. Recovery of a lost own log or reuse of a machine ID needs a separate specification.

Only available records participate while offline. Two machines can temporarily have different dictionaries. Once they have the same record set, their dictionaries must be equal regardless of fetch, send, retry, duplicate, or disconnect order. No server round trip is required for local learning. No server endpoint, wire format, authentication scheme, acknowledgment format, or new transport API is selected by this spec revision. Those require their own cards and review. This design does not authorize an external conversion API to receive dictionary or typed text.

### Operating notes (for PLAN step 4, not for cards)

- An IME holds its dictionary in memory and rewrites the whole file. After `sync` writes the IME file, the IME must reload it before it saves again. skkeleton reloads when the file's mtime changes. libskk reloads when the ETag changes, and a stale ETag makes its save fail rather than overwrite. CorvusSKK's `imcrvmgr.exe` must be stopped before the file is written. The restore and delete guards are the safety net, not the plan.
- Writing the owner's real IME files needs the owner's approval (PLAN question 6).
- `sync` stamps an IME's changes with the time of the import, not the time of the keystroke. Run it often, for example from a file watcher.

## CLI (`src/main.rs`)

```
jisyo check <file> [--encoding euc-jp|euc-jis-2004|utf-8|utf-16le]
jisyo sync --store <dir> --machine <id> --target corvus|fcitx5|skkeleton --file <path> [--max-deletes <n>] [--skip-unparsed] [--confirm-delivered-deletes] [--dry-run]
jisyo export --store <dir> --target corvus|fcitx5|skkeleton --out <path>
jisyo repair-log --store <dir> --machine <id>
```

`sync` is local IME reconciliation against the cached records, not a request to contact the server. `--confirm-delivered-deletes` defaults to false and applies only to the current invocation's actual diff. Use it only to confirm intentional purges of delivered candidates still missing from the IME file; never add it to an automatic watcher. It does not bypass --max-deletes, the unparsed-line guard, or --dry-run. A confirmed dry run reports the deletes that would be recorded and writes nothing. No confirmation is saved for a later invocation.

Output goes to stdout, one `<name> <value>` line per item, and contains only counts and names:

- `check`: `encoding <euc-jp|euc-jis-2004|utf-8|utf-16le>`, `bom <yes|no>`, `lines <n>`, `entries <okuri-ari> <okuri-nasi>`, `comments <n>`, `other <n>`, then `round-trip ok` when `write(read(file))` equals the file's bytes, else `round-trip failed` and exit 1.
- `sync`: `added`, `promoted`, `deleted`, `annotated`, `restored`, `skipped` (numbers), `written <yes|no>`, `bootstrap <yes|no>`.
- `export`: `skipped <n>`.
- `repair-log`: `removed <n>`.

An `Error` prints `error: <Display>` on stderr and exits 1. Bad arguments print `error: usage` and the four usage lines above on stderr, and exit 2. `main.rs` holds the only `Clock` that reads `SystemTime::now()`.
